# E1 — Análise da demanda

Demanda (literal): "siga" — à recomendação de fazer a B-15 antes da B-14: "Harness de desenvolvimento no Windows
nativo (temas T1–T8 da auditoria, lado `.claude/`)", absorvendo os achados (3)–(8) da B-18, cada um com teste.

Problema por trás: nesta máquina Windows o harness de desenvolvimento só funciona por muletas fora do repositório, e
onde não há muleta ele falha em silêncio. Medido em 2026-10-09:
- `python3` só existe pelo atalho local `~/bin/python3` (sh → `python.exe`, criado na auditoria; não versionado). Sem
  ele, os hooks de `.claude/settings.json` (comando `python3 …`) saem 127 e o Claude Code segue — os guards ficam
  ABERTOS. O atalho não vale para `subprocess` do Python nem para a ferramenta PowerShell.
- O portão das features do Windows rodou no WSL: `local/portao-win-motor-copia/portao.out` mostra
  `Python 3.10.12` nas duas passadas (`regua.json:3` exige `python3` e `/usr/bin/python3`; no Windows nativo não
  existe `/usr/bin/python3` ⇒ VERMELHO sempre). A régua nunca rodou no Windows nativo.
- Os scripts gravam o estado com CRLF: `git ls-files --eol` acha 7 arquivos `w/crlf` e 1 `w/mixed`, todos escritos
  pelo harness (`features.json`, `RESUME.md`, `LAST_DELIVERY.md`, `logs/custo.jsonl`, `logs/sessoes.jsonl`,
  archives, `campanhas/README.md`); o `.gitattributes` só cobre `.claude/tools/ac/**`.
- Enforcement cego no Windows: `guard-git.sh` só no matcher `Bash` (git push/reset pela ferramenta PowerShell não
  passam), guard de privacidade não reconhece `C:\Users\…` (o repositório é PÚBLICO), `bash_exe()` aceitaria o
  alias do WSL em `WindowsApps\bash.exe`.
- Há 2 arquivos sujos que já atacam parte disto (`_comum.sh`: `PY` com fallback para `python` + `PYTHONUTF8=1`;
  `package.sh`: usa `$PY`) — sem teste e fora de feature.

O que NÃO é: não é o produto (`scripts/`, `SKILL.md`, `references/`, `.claude/package/` — B-14); não toca o motor
embutido `.claude/tools/ac/` (cópia; os achados (1)(2) da B-18 vão ao BACKLOG do `auto-correcao`); não resolve a
dependência de `make` das suítes do produto (B-17); não publica pacote (B-08); não muda o comportamento no
macOS/Linux/WSL (lá `python3`, `/usr/bin/python3` e `bash` continuam como hoje); não depende do atalho
`~/bin/python3` — o critério é o harness funcionar sem ele.

Perguntas abertas (máx. 3, só as que mudam o desenho):
1. Uma feature só ou duas?
   → recomendo: uma feature `win-harness`, com até 3 grupos de correção em arquivos disjuntos (hooks e settings ·
     tools e estado · régua/portão/install e suíte harness-dev) — o critério de aceite é um só ("o harness roda no
     Windows nativo sem o atalho"), e uma metade sem a outra não é verificável no Windows (a régua é quem prova os
     hooks). Hipótese de tamanho: ~20 arquivos do `.claude/` (a E2 mede).
     alternativa: duas features em sequência (`win-harness-hooks` → `win-harness-regua`), menores e entregues antes,
     ao custo de a primeira ser validada no WSL.
2. Quantos Pythons a régua exige no Windows?
   → recomendo: a lista de interpretadores vira por plataforma — no Windows, os encontrados entre `python3`,
     `python` e `py -3`, sem repetir o mesmo executável, no mínimo 1; o portão imprime quais rodaram. No
     macOS/Linux/WSL continua `python3` + `/usr/bin/python3`. Medido: nesta máquina há 1 Python (3.12.7).
     alternativa: exigir 2 também no Windows (instalar um 3.9 pelo `py` launcher) — mais forte na compatibilidade
     com 3.9, mais configuração por máquina.
3. Até onde vai o `.gitattributes` (LF)?
   → recomendo: `.claude/**` e `campanhas/**` com `text eol=lf`, e os scripts do harness gravando com
     `newline="\n"` — resolve os 8 arquivos medidos e o `portar.sh` sem tocar o produto; o repositório inteiro fica
     com a B-14 (renormalizar o produto colide com ela).
     alternativa: `* text=auto eol=lf` no repositório inteiro agora (um renormalize só, mas mexe em arquivos do
     produto dentro desta feature).
