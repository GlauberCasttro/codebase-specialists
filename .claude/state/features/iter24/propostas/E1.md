# E1 — Análise da demanda

Demanda (literal): "Siga com sua recomendacao de prioridade" — recomendação: hotfix de segurança do guard (B-44 + B-45
+ B-47) antes da iter23; e "ok"/"a" para suspender a criação da iter23.

Problema por trás: a auditoria da cobaia .NET (0.12.0, 2026-10-12, verificação cega E2) provou que as garantias do
harness gerado são contornáveis pelo próprio agente: um subagente executa atos que só o humano pode fazer
(`waive-verify`, `accept`, `submit` alheio) chamando o cs-state por `bash`/`sh`/`python3 -m`/`python3 -W`; um hardlink
dentro do território do subagente sobrescreve `.claude/settings.json` e desliga os hooks; o agente principal escreve e
commita os registros de aprovação humana (`approvals.jsonl`, `acceptance.json5`…); e `git config core.hooksPath` desliga
o pre-commit. Tudo o que o harness promete ("o agente não se auto-aprova", "o humano decide no portão") fica sem efeito.

O que NÃO é: não é o fluxo da árvore (iter23: B-19, B-28, B-39..B-43); não é o teste .NET falso verde (B-48), a lição
que vira falha de código (B-49), a perda de dados de sessão/lições (B-50) nem os médios/baixos agrupados (B-51); não é
"escrita por Bash em geral" (limite declarado do projeto: o guard de Edit/Write não vê Bash) — só as formas que o
pre-bash PROMETE barrar e não barra; não é a política de branch para o principal trocar de branch (parte "falso
bloqueio" do B-47 fica para depois, salvo decisão em contrário).

Perguntas abertas (máx. 3, só as que mudam o desenho):
1. Escopo: entram B-46 (escritores e interpretadores não modelados: `git diff --output`, `curl -o`, `python3 -Sc`,
   `| sh -`) junto com B-44/B-45/B-47?
   → recomendo: SIM — é a mesma classe ("o pre-bash promete barrar e não barra"), no mesmo arquivo (bashscan.py), e
     deixá-la aberta mantém o hardlink/escrita protegida por outra porta.
     alternativa: só B-44/B-45/B-47 (menor, mais rápido).
2. Política para comando que o guard não consegue analisar (wrapper de shell, `-m`, stdin, flags combinadas):
   recusar sempre (fail-closed) ou só quando o alvo é harness/área protegida?
   → recomendo: recusar quando o comando invoca o harness (cs-*, .swarm/harness/*) por qualquer forma que não seja o
     caminho direto do binário, e fail-closed para interpretador com código inline/stdin — evita falso bloqueio de
     `bash scripts/build.sh` legítimo.
     alternativa: fail-closed para todo wrapper de shell (mais seguro, mais falso bloqueio).
3. Git: além de barrar `core.hooksPath`, push para main por refspec, `--no-verify`, `branch -D`, `remote set-url`,
   liberar o principal para TROCAR de branch (checkout/switch com árvore limpa)?
   → recomendo: NÃO nesta feature — liberar é mudança de política (relaxa o guard); fica como item do B-47 para
     decisão separada; aqui só fechamos as portas.
     alternativa: incluir a troca de branch agora.
